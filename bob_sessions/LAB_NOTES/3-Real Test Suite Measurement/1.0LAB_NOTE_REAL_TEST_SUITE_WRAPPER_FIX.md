# Lab Note — Real Test Suite Measurement & Identity Propagation Fix

**Project:** EcoPrint Transparency / SigSense  
**Test Type:** Real developer workflow validation — full repository test suite  
**Platform:** macOS  
**Date:** 2026-09-27  
**Status:** PASS — wrapper regression fixed; measurement-window limitation identified

---

## 1. Objective

Validate that the EcoPrint Transparency CLI can execute the repository's real full test suite without changing the workload's behavior.

The test also validates that workload identity propagation does not leak the outer EcoPrint execution identity into nested library/test operations.

A secondary objective is to identify whether very short developer workflows are captured by the current SigSense sampling cadence.

## 2. Developer Workflow Under Test

The repository's standard test command is:

```bash
npm test
```

which invokes:

```text
node --test tests/**/*.test.js
```

The EcoPrint measurement command is:

```bash
node bin/ecoprint.js run --name full-test-suite -- npm test
```

This represents the intended developer workflow:

```text
Developer
   ↓
npm test
   ↓
EcoPrint Transparency wrapper
   ↓
SigSense measurement
   ↓
Telemetry + attribution + reporting
```

## 3. Initial Observation

Before the fix, the full suite passed when run directly but failed when run through the EcoPrint wrapper.

The two failing tests were:

```text
compares the actual baseline measurement sources in deterministic insights

persistent workload baselines —
reuses a named workload and compares its next completed run
```

Both failures reported:

```text
SQLITE_CONSTRAINT: UNIQUE constraint failed: runs.run_id
```

This established that the failure was introduced by the wrapper execution path rather than by the underlying tests themselves.

## 4. Root Cause

The EcoPrint wrapper propagated:

```text
ECOPRINT_WORKLOAD_ID
ECOPRINT_RUN_ID
ECOPRINT_ATTEMPT_ID
```

to the child process.

`runUnderTransparency()` then treated those ambient environment variables as the identity for API calls made inside the child workload.

Some tests intentionally perform multiple runs against the same database. The nested calls therefore attempted to reuse the outer execution's `run_id`, producing duplicate unique-constraint failures.

Conceptually:

```text
EcoPrint outer run
      ↓
ECOPRINT_RUN_ID
      ↓
npm test child process
      ↓
test invokes Transparency API
      ↓
outer run_id reused
      ↓
second run attempts same run_id
      ↓
SQLITE_CONSTRAINT
```

## 5. Fix

The fix changed the Transparency library behavior so that `runUnderTransparency()` does not automatically consume ambient process identity.

Instead:

- the library defaults to no ambient identity;
- callers may explicitly provide an identity source;
- the actual `bin/ecoprint.js` CLI entry point explicitly supplies `process.env`.

This preserves intentional identity propagation for actual EcoPrint CLI executions while preventing nested library operations inside a measured workload from accidentally reusing the outer execution IDs.

A regression test was added to `tests/cli.test.js`.

No SigSense files were changed.

## 7. Important Measurement Finding

The successful wrapped test suite completed in approximately:

```text
637 ms
```

The EcoPrint report showed:

```text
Measurement: unavailable
Grid: unavailable
No SigSense observations in execution window.
No measurements fabricated.
```

This is an important limitation of the current telemetry capture path.

The full test suite executed correctly, but the workload completed before SigSense produced a qualifying telemetry observation inside the execution window.

This means:

> A successful workload execution does not automatically guarantee that a measurable telemetry interval will exist.

This is distinct from the wrapper regression.

## 8. Interpretation of the Short-Workload Limitation

The current SigSense path samples on an approximately one-second cadence.

As a result, very short workloads may complete between qualifying samples.

A workload shorter than one sampling interval is therefore at risk of producing:

```text
No SigSense observations in execution window.
```

The exact threshold is not simply "one second" because process startup, sampler phase, boundary timing, and telemetry flush behavior also affect whether an observation overlaps the measured execution window.

Therefore the correct conclusion is:

> **Very short workloads can currently be unmeasurable because the execution window may contain no qualifying telemetry interval.**

This should not be solved by fabricating an interval or extrapolating from no data.

## 9. Product Implication

The limitation matters directly to the intended developer workflow.

EcoPrint is intended to measure commands such as:

```text
build
test
deployment
lint
package installation
CI steps
```

Some of these operations can complete very quickly.

Therefore the measurement layer needs a defined strategy for short-lived workloads.

Possible future strategies include:

1. Increase telemetry sampling frequency.
2. Capture a qualifying sample immediately around workload start/end when technically valid.
3. Coordinate sampler timing with explicit workload run markers.
4. Maintain a continuously running telemetry stream and correlate the execution window against it.
5. Define and document a minimum measurable workload duration.
6. Preserve `unavailable` when evidence is insufficient.

The preferred strategy should preserve measurement correctness and avoid inventing energy.
