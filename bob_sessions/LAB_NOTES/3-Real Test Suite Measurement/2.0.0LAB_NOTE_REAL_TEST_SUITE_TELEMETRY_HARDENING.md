# LAB NOTE — Real Test Suite Telemetry Hardening & Short-Workload Capture

## Purpose

Document the investigation and fix for a telemetry-capture bottleneck discovered while measuring the real EcoPrint Transparency test workflow.

The goal was to determine why short-lived developer workloads sometimes reported **No SigSense observations in execution window** while longer runs successfully reported live hardware telemetry, and then harden the measurement path without fabricating measurements.

## 1. Initial Problem

The real Transparency CLI workflow was:

```bash
node bin/ecoprint.js run --name full-test-suite -- npm test
```

The complete suite was healthy. After the hardening work, the suite contained **244 passing tests across 56 suites**.

The problem was measurement capture, not test correctness.

Normal `npm test` execution was very short. A shell timing measurement showed:

```text
npm test  1.33s user 0.37s system 196% cpu 0.869 total
```

Several wrapped runs produced no telemetry observations at approximately:

- 0.67 s
- 1.29 s
- 1.90 s
- 2.47 s

A 3.0 s run eventually produced one hardware observation.

This initially suggested a simple minimum-duration threshold, but that was not the correct model.

## 2. Investigation

The investigation exposed an important database-path distinction.

The repository contains separate data stores for SigSense telemetry and Transparency identity/attribution.

The repository-local:

```text
sigsense/engine/ecoprint_telemetry.db
```

contained only five stale rows from 2026-09-26 and therefore was not the live source responsible for the current hardware measurements.

The Transparency telemetry adapter also contains the macOS installed-service path:

```text
/Library/Application Support/EcoPrint/Data/ecoprint_telemetry.db
```

The live Transparency CLI was therefore using the protected SigSense service/telemetry path rather than the stale repository copy we initially queried.

The investigation then reproduced the behavior against the live macOS SigSense service.

## 3. Root Cause

The primary bottleneck was an **END/flush timing boundary**, not simply “workloads shorter than one second cannot be measured.”

The macOS SigSense sampler uses a configured **500 ms powermetrics sample interval**.

Before the hardening change, the CLI could record the workload as finished and immediately query the telemetry window while a legitimate SigSense sample was still in flight.

Conceptually:

```text
workload starts
      |
      |---- real workload ----|
                           CLI END
                              |
                              | telemetry sample still finishing
                              |
                              |---- sample flush ---->
```

The query could therefore run before the final real sample was visible to the telemetry reader.

The investigation also established that a short workload may or may not overlap a real 500 ms hardware sample interval. Therefore, there is **no universal fixed “one-second minimum”** that guarantees a measurement.

The correct rule is:

> A short workload can be measured when a real telemetry sample interval has defensible temporal overlap with the execution window. If no such evidence exists, the result must remain unavailable.

## 4. Production Fix

### END becomes a real flush barrier

Every IPC `END` now waits for any in-flight telemetry sample to drain and flush before acknowledging the command.

This ensures the subsequent Transparency telemetry query sees legitimate data that belongs to the completed execution window.

### macOS sample intervals are treated correctly

The integration now accounts for powermetrics’ configured **500 ms interval**.

Idle time between polls is not treated as measured energy.

Fallback readings that do not have a measured interval contribute no integrated energy.

### Boundary behavior is covered by regression tests

Regression coverage was added for:

- END/query ordering
- sub-second telemetry interval clipping
- END behavior while another workload remains active
- preserving unavailable results when there is no defensible telemetry evidence

The raw SigSense schema and existing attribution/environmental reconciliation rules were preserved.

## 6. Remaining Limitation

The hardening does **not** guarantee telemetry for every extremely short workload.

A separate approximately 496 ms validation run produced no overlapping hardware interval and correctly reported telemetry as unavailable.

That behavior is intentional.

The system must not:

- invent a one-second interval;
- assume a sample represents time that was not actually measured;
- copy a nearby sample into the execution window without defensible temporal overlap;
- fabricate power, energy, carbon, or water values.

The remaining limitation is therefore tied to the cadence and phase of the underlying hardware telemetry source.

Future work should make short-workload capture more consistently overlap real telemetry intervals while preserving the same evidence and no-fabrication guarantees.

## 7. What We Learned

The investigation changed the interpretation of the original failure.

The earlier results did **not** establish that Transparency cannot measure workloads below one or two seconds.

Instead, they established that the CLI could finish and query its execution window before an in-flight hardware telemetry sample had been flushed, and a very short workload may also finish without any real sample interval overlapping it.

After the fix, a 691 ms real CPU workload produced valid hardware telemetry, while a 1.44 s real test-suite workflow produced one real observation.

This is a more defensible measurement architecture because telemetry availability now depends on actual observed intervals rather than an arbitrary duration threshold.

**Resolved for the current hackathon architecture, with a known future measurement-cadence limitation.**

The Transparency CLI now:

- measures real workloads through the live SigSense service;
- waits for legitimate in-flight telemetry to flush at END;

- maintains deterministic attribution and environmental reconciliation;
- passes the full automated test suite.
